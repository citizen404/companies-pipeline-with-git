# Companies data pipeline

Загрузка каталога компаний из постраничной JSON-выгрузки (`data/page_001.json` …
`page_020.json`) в PostgreSQL и три аналитических запроса поверх неё.

`review.csv` из исходного архива не используется — по условию задания смотрим
только на JSON-файлы.

## Данные

Каждый `page_XXX.json` — объект вида:

```json
{
  "page": 1,
  "per_page": 50,
  "total": 1000,
  "items": [
    {
      "id": "c_000001",
      "name": "ООО «Прайм Медиа»",
      "category": "Типография",
      "city": "Челябинск",
      "address": "ул. Южная, д. 96",
      "rating": 4.1,
      "reviews_count": 191,
      "site": null,
      "phone": "+7 (495) 248-44-40"
    }
  ]
}
```

20 страниц × 50 записей = 1000 записей, пагинация (`page`/`total`) консистентна
по всем файлам. В сырых данных 6 полных дублей (одинаковые `id` и все
остальные поля) — после дедупликации 994 уникальные компании.
`rating` и `site`/`phone` могут быть `NULL`.

## Схема БД

`schema.sql`:

- `categories(id, name)` — справочник категорий (22 значения)
- `cities(id, name)` — справочник городов (20 значений)
- `companies(id, name, category_id, city_id, address, rating, reviews_count, site, phone, loaded_at)`
  — основная таблица, `id` из исходных данных используется как PRIMARY KEY

Дедупликация — на двух уровнях:
1. `PRIMARY KEY (id)` + `ON CONFLICT (id) DO UPDATE` в `load.py`: повторная
   загрузка того же `id` обновит запись, а не создаст дубль.
2. `UNIQUE (name, city_id, address)` — страховка на случай, если одна и та же
   компания попадётся под разными `id`.

Индексы: `category_id`, `city_id`, `reviews_count` — под запросы из
`queries.sql`, плюс частичный индекс по `category_id WHERE site IS NOT NULL`
для запроса про долю компаний с сайтом.

## Запуск

### 1. Поднять Postgres

```bash
docker compose up -d
```

Схема (`schema.sql`) применится автоматически при первом старте контейнера
(через `docker-entrypoint-initdb.d`). Postgres слушает `localhost:5432`,
база/юзер/пароль — `companies`/`companies`/`companies` (см. `.env.example`).

### 2. Загрузить данные

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python load.py --data-dir ./data --dsn "postgresql://companies:companies@localhost:5432/companies"
```

Скрипт идемпотентен — его можно запускать повторно (например, при появлении
новых страниц), дубли не создаются.

### 3. Выполнить аналитические запросы

```bash
docker exec -i companies_db psql -U companies -d companies < queries.sql
```

или через любой psql-клиент, подключившись по DSN из `.env.example`.

## Структура репозитория

```
.
├── data/               # исходные page_001.json..page_020.json
├── schema.sql          # DDL: таблицы, индексы, констрейнты
├── load.py             # скрипт загрузки (парсинг + upsert)
├── queries.sql         # 3 аналитических запроса
├── docker-compose.yml  # локальный Postgres
├── requirements.txt
├── .env.example
└── README.md
```

## Примечания / что можно улучшить дальше

- Для по-настоящему больших выгрузок `load.py` стоит переписать на
  батчевую вставку с `COPY` вместо `execute_values`.
- Сейчас справочники (`categories`, `cities`) наполняются "на лету" при
  каждой загрузке — для продакшена их можно вынести в отдельную миграцию.
- Логика дедупликации рассчитана на точные дубли; для fuzzy-дедупликации
  (опечатки в названии/адресе) потребуется отдельный шаг с нормализацией
  строк или триграммным сравнением (`pg_trgm`).
