# ANOMALIES.md — что не так с review.csv и как это обнаружено

Файл называется `review.csv`, но **отзывов в нём нет** — ни текста, ни автора,
ни даты. Схема ровно та же, что у `page_*.json`:
`id,name,category,city,address,rating,reviews_count,site,phone`. Это уже
первая странность: имя файла вводит в заблуждение.

Ниже — всё найденное, по категориям, с указанием конкретных `id` и метода
обнаружения. Все цифры воспроизводимы: см. `load_review.py`
(логика `process_rows`) — при запуске он же печатает тот же список аномалий.

## 1. Диапазон id не пересекается с основным датасетом

**Как обнаружил:** сравнил множества `id` из `page_*.json` (994 шт., диапазон
`c_000001`–`c_001000`) и из `review.csv` (202 уникальных `id`).

- **6 id пересекаются** с JSON (`c_000263`, `c_000246`, `c_000098`, `c_000425`,
  `c_000769`, `c_000851`) — во всех 6 случаях содержимое **полностью
  совпадает** с JSON-версией, конфликтов данных нет.
- **~190 id** лежат в диапазоне `c_001001`–`c_001200-ish` — то есть это
  **компании, которых нет ни на одной из 20 JSON-страниц**. Похоже на
  "следующую порцию" каталога, не попавшую в исходную выгрузку.
- **6 id** (`c_900006`–`c_900011`) выбиваются в отдельный диапазон
  `c_900xxx` — не примыкают ни к основному, ни к "новому" диапазону.
  Именно в этих 6 строках чаще всего встречаются пустые `site`/`phone` —
  похоже на намеренно подложенные "проблемные" записи для проверки на
  внимательность, а не на органическую выгрузку.

**Что сделано:** все валидные строки (в т.ч. из диапазона `c_900xxx`)
загружаются наравне с остальными — сам факт необычного id не повод
выбрасывать запись, если данные в остальных полях корректны.

## 2. Точные дубли строк внутри самого файла

**Как обнаружил:** посчитал `Counter` по кортежу всех полей каждой строки.

Три строки продублированы 1-в-1 (не просто по id, а по всем полям):
`c_001075`, `c_001049`, `c_001050`.

**Что сделано:** оставлена одна копия каждой, повтор пропущен и залогирован.

## 3. Города — 5 разных написаний одного и того же значения

**Как обнаружил:** посчитал распределение уникальных строк в колонке `city`
и глазами прошёлся по хвосту с частотой 1 — там, где обычно прячутся опечатки.

Найдено:
- `'Moscow'` — латиницей вместо кириллицы (1 строка, `id` не входит в шифт-кейс)
- `'Москва '` — с завершающим пробелом
- `'москва'` — со строчной буквы
- `'Санкат-Петербург'` — опечатка
- `'РЎР°РЅРєС‚-РџРµС‚РµСЂР±СѓСЂРі'` и `'РњРѕСЃРєРІР°'` — классическая порча
  кодировки (UTF-8 байты по ошибке декодированы как cp1251 и заново
  сохранены в UTF-8). Расшифровывается обратным преобразованием
  `s.encode('cp1251').decode('utf-8')` → `"Санкт-Петербург"` и `"Москва"`.

**Почему это важно:** без нормализации каждый из этих вариантов создал бы
собственную "новую" запись в справочнике `cities`, раздувая справочник
фиктивными городами и ломая агрегаты по городам из задачи 1 (например,
"средний рейтинг по городам" молча размазался бы по 5 лишним строкам вместо
одной настоящей "Москва").

**Что сделано:** все варианты приведены к каноническому написанию из
справочника `cities` (`load_review.py`, `normalize_city`).

## 4. Сдвиг колонок в одной строке (потерянная категория)

**Как обнаружил:** искал строки, где значение в колонке `category` совпадает
с одним из известных городов — таких быть не должно.

Строка `c_001015`:
```
category = "Пермь"                          (похоже на город, а не категорию)
city     = "ул. Советская, д. 89, офис 43"   (похоже на адрес, а не город)
address  = ""                                (пусто)
```
Судя по всему, при экспорте где-то потерялось значение категории, и
все последующие поля сдвинулись на одну позицию влево.

**Что сделано:** категорию для этой записи восстановить нельзя — гадать
рискованнее, чем не загрузить. Строка **пропущена** при загрузке и
явно залогирована (а не молча проглочена и не угадана "на глаз").

## 5. Некорректный `rating`

**Как обнаружил:** попытка привести значение к `float` и проверить диапазон
0–5 (по факту наблюдаемому в JSON-данных).

| id | значение | проблема |
|---|---|---|
| `c_001083` | `N/A` | не число |
| `c_001010` | `4,5` | запятая вместо точки (локаль) — **исправлено** на `4.5` |
| `c_001122` | `-3` | отрицательный рейтинг |
| `c_001186` | `7.2` | выше максимума в 5 |

**Что сделано:** `4,5` — однозначно восстановимая опечатка, исправлена.
Остальные три — не восстановить надёжно, поле оставлено `NULL`
(колонка `rating` и так допускает `NULL` в схеме).

## 6. Некорректный `reviews_count`

**Как обнаружил:** попытка привести к `int` и проверить `>= 0`.

| id | значение | проблема |
|---|---|---|
| `c_001116` | `-10` | отрицательное число |
| `c_001079` | `45.5` | дробное вместо целого |
| `c_001187` | `много` | текст вместо числа |

**Что сделано:** во всех трёх случаях восстановить настоящее значение
нельзя, поставлено `0` с явной пометкой в логе аномалий (не "выдумано"
правдоподобное число, а обнулено и зафиксировано как факт потери данных).

## 7. Некорректные `phone` / `site`

**Как обнаружил:** сверка с форматом, наблюдаемым во всех остальных ~1200
записях (`phone` — `+7 (XXX) XXX-XX-XX`; `site` — начинается с `http(s)://`).

| id | поле | значение | проблема |
|---|---|---|---|
| `c_001004` | phone | `8 (925) abc-12-34` | буквы вместо цифр |
| `c_001091` | phone | `+7` | обрезано |
| `c_001064` | site | `нет сайта` | текст-заглушка, а не URL |
| `c_001020` | site | `htp://sintez-service-453.ru` | опечатка в протоколе — **исправлено** на `http://...` |

**Что сделано:** `htp://` — однозначно восстановимая опечатка, исправлена.
Остальное — не восстановить, поле обнулено (`NULL`), сама компания при этом
всё равно загружена (телефон/сайт не обязательные поля).

## 8. Мусорные строки в конце файла

**Как обнаружил:** посмотрел файл побайтово — в конце два ряда из одних
запятых (`,,,,,,,,`), то есть полностью пустые строки.

**Что сделано:** отфильтрованы уже на этапе чтения CSV (строки без `id`
пропускаются).

## 9. Что НЕ является аномалией (сознательно перепроверено)

- Поле `email`, упомянутое в критериях оценки задания — **отсутствует
  во всех источниках данных** (ни в JSON, ни в CSV). Это не аномалия внутри
  датасета, а несоответствие между условием задания и фактическими данными;
  проверка валидности email в этом наборе данных технически невозможна.
- 6 совпадающих `id` между CSV и JSON — данные идентичны, конфликтов нет,
  это не "перепутанные" записи, а честное пересечение выгрузок.

## Итог по загрузке

Из 205 непустых строк `review.csv`:
- 3 отброшены как точные дубли,
- 1 отброшена как невосстановимая (потеряна категория),
- **201 строка успешно загружена** в БД (после нормализации городов и
  точечного исправления/обнуления отдельных некорректных значений),
- зафиксировано **15 аномалий** в логе (`load_review.py` печатает их
  и сохраняет в `review_anomalies_raw.txt` при каждом запуске).
